# ADR-001 — Isolated LibeTech AI OS foundation

Status: Local implementation decision under the Chairman's new-build instruction; production adoption pending.
Decider for business adoption: Chairman. Implementer: Codex.

Build a new modular application with one domain service used by web and API clients. Reuse verified concepts from AiTogether, not its unaudited auth routes or production data. Use PostgreSQL SQL with mandatory tenant/project scope, UUIDs, timestamptz and append-only events. Use a connection pool when configured with a PostgreSQL server.

For the reviewable local build, PGlite runs the same SQL in an embedded PostgreSQL runtime with persistent files. This is not a production topology or proof of concurrency/load on a PostgreSQL server. Local demo identities are synthetic and disabled outside loopback. No password workaround or default production account is introduced. Production requires organization identity, secret provisioning, server PostgreSQL verification, staging isolation tests, restore rehearsal and UAT.

Data ownership is provisional for synthetic data only. Current workbook/tickets/Vault remain their own sources until an approved cutover. Z2 summaries are generated by the analytics projector. Future AI suggestions belong in Z4; a bot service account is read-only in this slice.

References: `SPEC-001-foundation.md`; prior LibeTech AI OS scope and source reviews delivered 2026-11-08. Official implementation references: https://pglite.dev/docs/api ; https://nextjs.org/docs/app/api-reference/functions/cookies .


## Alternatives and consequences

| Option | Strength | Cost / limitation | Decision |
|---|---|---|---|
| Revive the old lab directly | Might preserve deployed data and team context | Access/runtime identity unverified; would couple the new build to an unknown instance | Do not infer shutdown or modify the old instance |
| New modular Next.js + PostgreSQL foundation | One domain implementation for web/API; clear ownership and migrations; matches existing team concepts | Requires separate source reconciliation, SSO and production integration | Selected for the local build |
| Separate services from day one | Independent scaling and deployment | More identity, queue, observability and operational overhead before real usage evidence | Revisit only at a measured boundary |
| Containerized PostgreSQL for local review | Closest server topology | Docker runtime access/setup not established here | Use later for staging/integration tests |
| PGlite for local review | Real SQL/RLS and persistent files; no external DB or credentials | Single local process, no proof of server concurrency/HA/backup | Selected strictly for synthetic local use |

Consequences: foundation code is reviewable and runnable now. It is not a production acceptance. PGlite, memory sessions, demo assignments and inline CSP allowances must not be carried into public production unchanged. Production membership/identity, server pool/RLS tests, projector credentials, nonce CSP, restore and source cutover have explicit gates in `IMPLEMENTATION-ROADMAP.md`.
