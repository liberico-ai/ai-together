OQ-53 (PR "subject verification") — mechanism measurements on PostgreSQL 16, taken while planning (19/11/2026)
==========================================================================================================
What this is: measurements of the MECHANISM, taken by the planner before any product code or migration exists. They ran in a throwaway
schema (oq53_probe) that rebuilds the shape of the tables involved (projects, source events, revisions, a per-thread counter, a
position table, a decision table) inside the session's own isolated test database (127.0.0.1:55471, slice1_verify_531119). No
application table was read or written; the schema was dropped at the end of each run ("objects left: 0"). The behaviour of the real
SQL of migration 023 is to be proven by the native cases of the plan (docs/plans/oq-53-subject-verification.md), not by this file.
How: two node scripts with the `pg` client, several connections; kept next to this file (probe-1.cjs, probe-2.cjs). They read the
connection strings from the environment and print none. Run: `node <repo>/docs/reviews/oq-53-evidence-20261119/probe-1.cjs <out>`
with SLICE1_TEST_DATABASE_URL and SLICE1_WEB_DATABASE_URL set and NODE_PATH=<repo>/node_modules.
Lines below are the scripts' output as printed. One edit: the free-text tail of the second line of section 1 was shortened.

Reading of the numbers (planner; the plan states the design)
------------------------------------------------------------
1    A plain sequence does not give "readable after commit": the lower number became visible after the higher one.
2    One counter row per thread, updated inside the writing transaction and held to its commit: numbers follow commit order (0 violations
     in 20 forced rounds), no gap after a rollback, a new thread is safe with two writers, other threads are not held up (2 ms), a
     REPEATABLE READ writer that raced gets 40001, an abandoned writer costs the next writer of that thread 55P03 after 5 s.
3    A BEFORE INSERT trigger runs for a row that ON CONFLICT DO NOTHING then skips: the replay burns a number and waits on the counter.
     An AFTER INSERT trigger runs only for a stored row: a replay neither burns nor waits.
4    Confirm side as compare-and-set in an AFTER INSERT trigger of the decision table. FOR NO KEY UPDATE, FOR SHARE and FOR UPDATE close
     both directions; FOR KEY SHARE closes neither (it does not conflict with the counter update). One locking statement re-reads the
     row after its wait (4b). A rejection takes no lock (4c). Intake (project FK KEY SHARE, then thread) and confirmation (project
     NO KEY UPDATE, then thread) never wait on each other in a cycle (4d, 8). Raw transactions that write two threads in opposite
     order do deadlock and PostgreSQL cancels one (4e).
5    No libetech_* role can lock the counter row itself (42501 at every strength, also with SELECT granted) or call the function. With
     AFTER INSERT triggers the caller's own row-level security answers before any lock: an out-of-scope writer gets 42501 in 1-2 ms
     while the thread is held. With a BEFORE INSERT trigger the same writer waited 5 s on a thread it may not write (5d).
6    Side tables: 60 000 revisions in 4 000 threads numbered in 260 ms, the old table's file untouched, its inserts blocked for the
     length of the migration transaction and reads not. A column on the old table needs the immutability trigger disabled and writes
     every row again (table size x2).
7    FOR SHARE on the confirm side starves a writer of the thread when confirmations overlap (57014 after 9 s, 175 confirmations
     meanwhile); FOR NO KEY UPDATE serves it in arrival order (370 ms). With the project row lock of migration 022 taken first,
     confirmations of one project already run one at a time and neither strength starves.

One read-only probe (probe-3.cjs): no schema, no table, no role was created or altered; it only reads pg_stat_activity and pg_roles
from two superuser sessions of the same test database. It answers one question of the security gate's S-1: can migration 023 refuse

== 9. the refusal "a session of a role that is a member of libetech_ai is connected" (plan 0.2, P6; security gate S-1) ==
9a another superuser session only: check without "NOT rolsuper" counts 1 (pg_has_role is true for a superuser); with it: 0
9b the other session does SET LOCAL ROLE libetech_ai inside a transaction (what the tests' AI handle does): check counts 0; its usename is still the login
9c the other session does SET SESSION AUTHORIZATION libetech_ai: usename in pg_stat_activity = the operator login; check counts 0
9d the other session is libetech_runtime (not a member): check counts 0
9e members of libetech_ai among login roles today: 0

Reading (planner)
9    The check must exclude superusers (pg_has_role answers true for them: 9a), so it only sees a NON-superuser login that is a member
     of libetech_ai. No such login exists today (9e): the check always passes until the AI login exists. A session that merely does
     SET ROLE or SET SESSION AUTHORIZATION to libetech_ai keeps its login name in pg_stat_activity and is not seen (9b, 9c): the
     refusing branch cannot be exercised by a test without a real member login, which this PR does not create.
