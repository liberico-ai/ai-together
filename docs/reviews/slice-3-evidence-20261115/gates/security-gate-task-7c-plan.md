## Must change before code

### M1 — Self-proposal ban (S56) and project matching are bypassable by UUID case

Plan, step 5: «`userId===p.id` → `DOC_APPROVAL_PROPOSAL_INVALID`». Step 1 parses `userId`/`projectId` as `uuid`.

- #fact: zod in this repo is 4.6.7 and `z.uuid()` accepts upper-case hex (checked: `z.uuid().safeParse('3F2504E0-4F89-41D3-9A0C-0305E82C3301').success === true`).
- #fact: `p.id` comes from the DB (`identity.ts:50`), i.e. lower-case canonical text; PostgreSQL compares `uuid` case-insensitively, so `SELECT … FROM identity.users WHERE id=$1 FOR UPDATE` (step 6) finds the same row for either casing.
- **Abuse:** a project manager who holds no approval seat sends `userId` = their own id in upper case. Step 5 string comparison is false → passes. Step 6 loads their own row; they are an active, activated, non-viewer member of the project, not the account admin → eligible. A ballot granting themselves `doc_approve:*` is opened and DMs go to the BoM seats. S56 (fail-closed reading of the Chairman's OQ-31 rider) is broken; only the BoM vote and the admin apply remain as gates, and voters see a reason prefixed with the proposer's own name as proposer *and* (on the card) as subject — easy to miss.
- Same cause, second effect: steps 9 and `docApprovalProposals` compare `grant.projectId` (lower-case from DB) with the request `projectId`. An upper-case `projectId` passes step 3 (SQL) but finds no entry in step 9 → the defensive assertion throws → 500 `INTERNAL_ERROR`; the list silently returns empty.
- Pre-existing, same pattern: `accounts.ts:192` `cmd.userId!==p.id` for the admin. It fails closed today only by accident (excluding the admin's own seat leaves no chairman seat → `APPROVERS_NOT_READY`). Not in scope to fix, but worth one line in the task.
- **Smallest change to the plan:** state that every id comparison uses DB-returned ids: do the self check as `user.id===p.id` *after* step 6 loads the row (keep the same 422 sentence), or normalise `userId`/`projectId` to lower case in the zod schema (`.transform(s=>s.toLowerCase())`) and say so. Use the DB `project_id` from step 3 for all later comparisons. Add test cases (see T1).

### M2 — No defined way to close a coordinator's open ballot; a coordinator can block the admin's access changes for a member

Plan, step 11: shared body refuses `APPROVAL_PENDING` «khi đã có phiếu mở khác»; unique index `account_approval_active_access_change` (018:32-33) allows one open ballot per subject. The plan names no cancel, withdraw or supersede path.

- #fact: today an open `access_change` ballot ends only by (a) vote rejection, (b) 48 h expiry, (c) the subject's `account_version` changing, which the admin's next `propose_access_change` turns into `expired` (`accounts.ts:263-265`) and which `voteForPrincipal` closes on the next vote (`account-approval.ts:176-189`).
- **Abuse:** a manager of project A opens a doc-approval ballot for member X (pending, 48 h). The admin needs to widen X's access for another reason (e.g. add project B) → `APPROVAL_PENDING`. The admin's only lever is a version-bumping command on X (`revoke_sessions`, `access` reduction, …), which also revokes X's sessions and Telegram codes — an undocumented side effect used as a cancel button. When the ballot closes (rejection, expiry, bump) the manager can reopen at once (cap is 10/h per proposer), so a hostile or careless manager can keep X's access changes contested. Symmetrically, the admin's open ballot blocks the manager (that direction is fine).
- **Smallest change to the plan:** (1) state explicitly how an admin supersedes a coordinator ballot (today: any version-bumping account command, then propose), and test it (T6); (2) record «who may cancel/withdraw an open coordinator ballot» as an open question (Q2) instead of leaving it implicit; (3) optionally, if the session wants a clean lever without side effects, an admin-only `cancel_access_change` kind in `accounts.ts` (state → `rejected`/`expired`, audit event) — allowed by the constraints (no change to `account-approval.ts` or migrations, the identity role already has `UPDATE(state,updated_at)`), but that is a scope addition the session must choose, not the builder.

### M3 — The proposer's authority is read but not locked; a demotion racing the proposal is not handled or tested

Plan, step 3: «đọc `identity.memberships` nối `identity.users` cho `(p.id, projectId)`» — no lock stated. Step 6 locks only the subject.

- #fact: the admin path that changes the proposer's role (`command` → `access`) locks the proposer's `identity.users` row `FOR UPDATE` before rewriting memberships (`accounts.ts:193`, `:218`).
- **Abuse/race:** the admin demotes (or removes, or disables) the manager; in READ COMMITTED the manager's in-flight proposal read the old membership just before the admin committed and commits a ballot afterwards. A person who no longer coordinates the project has an open ballot that DMs all seats and that the admin may later apply from `/team` without noticing the proposer lost the role. The plan's test «the proposer's role is read from the database, not from the session» covers only the sequential case.
- **Smallest change to the plan:** in step 3 read the proposer row with `SELECT … FROM identity.users WHERE id=$1 AND active AND password_hash IS NOT NULL FOR SHARE` (or `FOR UPDATE`) before the membership read, so a concurrent `access`/`disable` on the proposer serialises with the proposal. Fix the lock order explicitly: proposer row, then subject row; refuse `userId === adminId` **before** locking the subject (see S2) to avoid an admin-row/proposer-row lock cycle. Add the native race case (T3). What happens to an already-open ballot when its proposer later loses the role is a policy question (Q3).

## Should change

- **S1 — Apply-time defence for coordinator ballots.** S65 says the scope of a coordinator ballot is enforced only in the service, at proposal time; the 019 guard only checks that some approved ballot names the code. Add to the plan, in `access` (accounts.ts, allowed): when the ballot's `proposer_id` is not the admin, require `docApprovalDelta(previous_grants, grants)` to be non-null, else `TELEGRAM_APPROVAL_REQUIRED`. Cheap, and it makes a future bug in the proposal path non-applicable rather than merely visible. Test in T8.
- **S2 — Subject = account admin must be refused before `FOR UPDATE`.** Step 6 locks the subject row first and only then rejects «là tài khoản quản trị». The admin's own commands lock the admin row first (`operator`, `accounts.ts:52`). With M3's proposer lock this forms a two-row cycle (manager: own row → admin row; admin acting on that manager: admin row → manager row) → `40P01` deadlock → 500. Compare `userId` (normalised) with `identity.adminId` before any lock; if `adminId` is undefined, refuse the whole command (fail-closed; `verifiedApprovalSeats` would refuse later anyway, but after DB work).
- **S3 — `23505` from the unique index must map to `APPROVAL_PENDING`.** The plan relies on the subject row lock to serialise and on the 018 unique index as backstop. If the backstop ever fires, `http.ts:12` answers `DUPLICATE_CODE` «Mã việc đã tồn tại trong dự án.» — wrong code and wrong sentence. Catch `23505` on the ballot insert in the coordinator path (or in `openAccessChangeBallot`) and throw `APPROVAL_PENDING`. Note in the plan that the replay check (step 10) is a read, not the idempotency mechanism; the mechanism is the row lock plus the unique index, which satisfies E-BE-08's intent. Say this in S58 so a reviewer does not flag it as SELECT-then-INSERT.
- **S4 — Basis text: reject control characters and U+0000.** `reason` is `z.string().trim()`; a basis with newlines can push fake lines under the server prefix on `/approvals` and `/team` (e.g. a line imitating an admin note), and U+0000 raises a raw PostgreSQL error → 500 (the same class S64 fixes for drafts). Specify: basis rejects `\p{Cc}` (incl. CR/LF/NUL) and lone surrogates → 422; render reason as plain text. The proposer's name is read from the DB and the prefix is first — good — but test with a basis that starts with another name plus «(quản trị tài khoản)» (T9).
- **S5 — Validate the frozen set with `grantsSchema` before freezing.** `access` re-parses `ballot.grants` and `previous_grants` with `grantsSchema` (max 30 entries, ≤11 permissions, unique project). If `before` violates it (legacy rows, duplicates), the ballot is created, voted, and then cannot be applied, after DMs went out. Parse `before` and `after` with `grantsSchema` in step 9; on failure use the step-6 sentence (no detail leak).
- **S6 — Spam limits beyond 10/h per proposer.** Each proposal DMs 2–4 seats; the cap is per proposer only and counts per hour, so N managers × 10/h, and immediate re-proposal after a rejection, are possible. Suggest one of: per `(proposer, subject)` cooldown after a `rejected` ballot (e.g. 24 h), or a per-proposer cap on concurrently open ballots. This is an abuse limit, not a voting rule. Also say the throttle is committed in its own transaction before the main one (existing pattern, `identity.ts:30-36`), so failed attempts still count — intentional, keep.
- **S7 — Seat-holding leak through `APPROVERS_NOT_READY`.** The shared body calls `verifiedApprovalSeats(tx,identity,user.id)`; if the subject holds a BoM seat and their exclusion leaves no eligible BoM seat, the manager gets `APPROVERS_NOT_READY` for that member only, which reveals the member holds a seat. Low impact; either accept and document it, or map that error, on the coordinator path only, to a neutral sentence. Decide in the plan, test either way.
- **S8 — `APPROVAL_PENDING` tells the manager that the member has some open access-change ballot**, possibly about another project the manager cannot see. The plan already strips content. Acceptable; state it as an accepted residual in the plan rather than leaving it implicit.
- **S9 — `docApprovalProposals` should hide stale ballots.** Filter `subject_account_version = users.account_version` (as `list`'s `accessChange` does) so a manager does not see a dead ballot as `pending`. Also cap at 50 and order deterministically (stated: cap; add order).
- **S10 — Return shape of the shared function.** `proposeAccessChange` returns `{user,…}` (username, version, active flags). State that `openAccessChangeBallot` returns only `{id, expiresAt, state}` and that the coordinator path never returns `user`, so the account version and username do not leak to the manager (the plan intentionally hides the version: step 7).

## Questions that are not the session's to decide

- **Q1 — OQ-35 (already open).** May a proposer who holds a BoM seat use this path, and if so do they vote on their own ballot (options (a)–(d) in OQ-35)? The placeholder S57 is correctly fail-closed (see «sound»); it only needs the Chairman's answer.
- **Q2 — Who may cancel or withdraw an open coordinator ballot?** Options: (a) nobody — only votes, 48 h expiry or an account change end it (today's behaviour); (b) the proposing manager may withdraw their own; (c) any manager of the same project; (d) the account admin, with a basis, as a dedicated command; combinations of (b)/(d).
- **Q3 — If the proposer loses the `manager` role, leaves the project or is disabled before the admin applies, does the ballot stay applicable?** Options: (a) yes, the admin still decides (today's behaviour by default); (b) the ballot expires automatically when the proposer's authority ends; (c) it stays, but `/team` must show that the proposer no longer coordinates the project.
- **Q4 — May a manager propose for another `manager` of the same project?** Two co-managers can propose for each other, which reaches the same outcome the S56 self-ban blocks for one person. Options: (a) allowed (only BoM vote and admin apply stand between); (b) refused for subjects whose role in that project is `manager`; (c) allowed, but the card says the subject is also a coordinator. Also pending: Chairman confirmation of S56 itself (the self-ban is an interpretation, `docs/OPEN-QUESTIONS.md:425`).

## Missing test cases

- **T2** — proposer account `active=false` or not activated (password hash NULL) while holding a still-valid principal object → 404 sentence, 0 ballots. The plan tests demotion, removal, bot, viewer, but not disabled/not-activated proposers.
- **T3 (M3, native)** — admin `access` demoting the proposer runs concurrently with `proposeDocApproval`: either the proposal commits first (then it was valid) or it sees the demotion (`MANAGER_REQUIRED`); never a ballot created after the demotion commits. Same for a concurrent admin `access` on the **subject** (read/freeze race on the subject's grants): the frozen `previous_grants` and `subject_account_version` equal the state the ballot was built from, and a later apply against the changed account is refused.
- **T4 (S2)** — `userId` = admin id → step-6 sentence; with a concurrent admin command no deadlock error (native).
- **T5 (S3)** — forced unique-index conflict (operator inserts an open ballot for the subject between the lock-free checks, or a stub) → `APPROVAL_PENDING`, not `DUPLICATE_CODE`/500.
- **T6 (M2)** — coordinator ballot open → admin `propose_access_change` for the same member → `APPROVAL_PENDING`; after the documented supersede step → admin proposal succeeds and the coordinator ballot is `expired`, with the `expiredApprovalIds` in the event. Plus whatever cancel rule Q2 yields.
- **T7** — a coordinator ballot whose subject's account version changed (admin reduced another permission) cannot be applied (`TELEGRAM_APPROVAL_REQUIRED`) and the voter card closes; `list.accessChange` is null for it.
- **T8 (S1)** — a ballot row with `proposer_id` = manager whose `grants` widen beyond `doc_approve:*` (inserted by operator login, simulating a proposal-path bug), voted approved by a BoM seat → admin `access` with exactly those grants is refused.
- **T9 (S4)** — basis containing CR/LF, U+0000, or text imitating another proposer prefix → 422 for control chars; for imitation text, `reason` begins with the DB name + «(điều phối dự án) trình:» and the imitation sits only after it.
- **T10 (S5)** — subject whose current grants fail `grantsSchema` (e.g. 31 projects or duplicate project rows if possible) → step-6 sentence, 0 ballots, 0 DMs.
- **T11** — input edges: `docTypes` empty → ZodError; `expectedTypes` containing types not held → `VERSION_CONFLICT`; `docTypes` ⊆ held → `ACCESS_CHANGE_NOT_NEEDED`; `reason` length 4 and 361 → ZodError; total frozen reason ≤ 500 with a 100-character name and 360-character basis.
- **T12 (S7)** — subject holds a BoM seat: assert whichever answer the plan chooses, and that the answer for another member in the same state of seat pairing does not differ except as documented.
- **T13** — the «failed proposal leaves nothing» snapshot must also include `identity.throttle` behaviour (count increments on failure, by design) and `identity.events` / `outbox_messages` / `account_approval_voters` — the plan says «chụp trước/sau cho từng nhánh lỗi»; list the branches explicitly (1,3,4,5,6,7,8,10-replay,11-pending, APPROVERS_NOT_READY) so none is skipped.

## Checked and found sound

- **Authority derivation (Q1 of brief).** Command is strict; `grants`, `role`, `reportPermissions`, `projectIds`, `proposerId`, `tenantId` are rejected (422). Tenant from service, actor from session id, role per project from `identity.memberships` + `coalesce(project_role, role)` in the transaction, not from `p.grants` (S55). Bot refused. Using per-project role instead of `p.role==='viewer'` is correct (multi-project principals get `viewer` as aggregate role, `identity.ts:50`). Cross-project reach: the only project parameter is checked against the proposer's own manager membership; the subject must have an entry in that same project; no second project parameter exists.
- **Subject eligibility.** One sentence for unknown id, other tenant, disabled, not activated, not a member, `viewer`, admin account, entries outside admin scope — no names, counts or states leak (step 6). Self refused (S56), subject to M1.
- **Scope of what can be proposed.** Server builds `after` from `before` read after the subject row lock; only `doc_approve:<type>` codes added to one existing entry; `docApprovalDelta` + `widensAccess` asserted before writing; freeze via the shared admin body freezes `subject_account_version`, `previous_grants`, `grants` (`accounts.ts:271-274`). Writers of memberships lock the user row first (`accounts.ts:193`, registration creates a new user), so the read/freeze is race-safe; apply additionally requires version, `grants` and `previous_grants` equality (`accounts.ts:211-213`). No removal, role change, other project or report permission is expressible.
- **Stale check without leaking the version.** `expectedTypes` compares exactly what the manager can see within the project; the version is still frozen in the ballot. Reasonable design.
- **Separation of duties.** Proposer cannot apply: `access` requires `p.id===adminId` and an active admin row (`accounts.ts:49-53`). Subject's seat excluded from voters (`account-approval.ts:37`, `:48`). Account admin always holds the chairman seat (`validSeats`, `:22`), so the admin can never take this path (step 4). Frozen voters, unexpired, tally re-checked at apply (`approvalReady`, `:95-105`). Admin applies the exact frozen set from `/team` (S60, button sends `accessChange.grants`), and voters see the same row's `grants`/`previous_grants` on `/approvals` (`:129-154`) — admin and voters see one source.
- **OQ-35 placeholder (S57).** Refusing any proposer with a row in `identity.account_approval_seats` is strictly tighter than every OQ-35 option, touches neither `accessChangeTally` nor voter selection, and only tells the proposer about their own seat — no disclosure of other seat holders. Seat rows change only through the operator login, so the unlocked read is adequate.
- **Replay (S58).** Two identical concurrent proposals serialise on the subject row lock; the second sees the committed ballot and replays; the 018 partial unique index is a real constraint backstop (with S3). Replay requires same proposer, same frozen sets, current version; different content → `APPROVAL_PENDING` without content.
- **Audit.** `proposer_id` column (FK to users, 009:15,22) and event `actor_id` record the proposer's id immutably; the event adds `via`, `projectId`, `addedTypes`. The name prefix in `reason` is display only and built from the DB.
- **Outbox/notifications.** DMs are enqueued in the same transaction by the unchanged `notifyVoters` (E-INT-06), with the existing dedupe key; a failed proposal rolls back DMs with the ballot.
- **Constraints.** Nothing in the plan requires changing `src/server/account-approval.ts`, `bot-plugin/`, or migration 019 (or adding a migration); every proposed fix above stays in `accounts.ts`, `access-grants.ts`, the new route and tests. Option M2(3) also stays within those limits.
- **No condition (c).** An approved ballot changes nothing; only the admin's `access` writes memberships, and the 019 guard is a second layer.
